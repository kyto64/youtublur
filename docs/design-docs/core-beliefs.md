# コア信念

プロジェクトの根底にある基本原則と信念。

## 基本理念

### 1. シンプルさ

複雑さは敵です。必要最小限の機能で、最大の価値を提供します。

- 不要な機能は実装しない
- シンプルな解決策を優先する
- 複雑なロジックは分割する

### 2. 明確性

コードもドキュメントも、明確であるべきです。

- 曖昧さを排除する
- 意図を明確に伝える
- 推測を必要としない

### 3. 堅牢性

予期せぬ状況にも耐えうるシステムを構築します。

- 境界でデータを検証する
- エラーを適切に処理する
- 安全なフォールバックを提供する

### 4. 保守性

将来の変更を容易にします。

- コードは読みやすく書く
- ドキュメントは最新に保つ
- テストは網羅的に書く

### 5. ユーザー中心

ユーザーの体験を最優先します。

- ユーザーの負担を減らす
- 直感的な操作を提供する
- 目に見える価値を提供する

## 技術的信念

### コード品質

- **DRY（Don't Repeat Yourself）**: 重複は技術的負債の根源
- **KISS（Keep It Simple）**: 複雑な解決策は疑う
- **YAGNI（You Aren't Gonna Need It）**: 今必要な機能だけを実装
- **単一責任の原則**: 一つの関数は一つのことだけを行う

### プロセス

- **自動化できることは自動化する**: 人間の時間は貴重
- **テストは必須**: 変更の安全性を保証する
- **ドキュメントはコードと共に**: 知識をコード化する
- **継続的改善**: 常により良い方法を探求する

### 拡張性

- **境界を意識する**: 明確なインターフェースで接続
- **疎結合で設計する**: 変更の影響範囲を最小限に
- **プラグ可能にする**: 機能の追加・置換を容易に

## AI駆動開発の原則

### エージェントとの協調

1. **漸進的開示**
   - 最小のエントリーポイントから始める
   - 必要に応じて文脈を段階的に提供
   - 情報過多を避ける

2. **明確な境界**
   - 各コンポーネントの責任を明確に
   - 制約は機械的に強制
   - 柔軟性は境界内で許容

3. **フィードバックループ**
   - エージェントの出力を検証
   - 改善点をシステムにフィードバック
   - ルールとツールを継続的に改善

4. **知識のコード化**
   - スクラム会議の議事録は要約してドキュメントに
   - 設計判断は ADR として記録
   - ベストプラクティスはリンターにエンコード

### リポジトリ構造の原則

```
AGENTS.md          # 最小のエントリーポイント（マップとして機能）
ARCHITECTURE.md    # 技術的概要
DESIGN.md          # 設計原則
QUALITY_SCORE.md   # 品質メトリクス
docs/              # 詳細なドキュメント
  design-docs/     # 設計ドキュメント
  exec-plans/      # 実行計画
  product-specs/   # 製品仕様
  references/      # リファレンス
```

## 価値観

### 人間の時間を尊重する

- 自動化で人間を解放する
- 機械に任せられることを機械に任せる
- 人間は創造的な作業に集中する

### 品質を妥協しない

- 迅速さと品質は両立できる
- テストは開発の一部、後付けではない
- 技術的負債は放置しない

### 透明性を保つ

- 決定の背景を共有する
- 失敗から学ぶ
- 知識をオープンにする

### 持続可能性を考慮する

- 長期的な維持管理を容易にする
- 過度な最適化を避ける
- シンプルを保つ

## 禁止事項

### 絶対にやってはいけないこと

1. **セキュリティの妥協**
   - 認証なしで外部にデータを送信する
   - 機密情報をコードにハードコードする
   - 入力値を検証せずに使用する

2. **品質の妥協**
   - テストなしでコードをマージする
   - 壊れたコードを本番にデプロイする
   - ドキュメントを放置する

3. **透明性の欠如**
   - 決定の背景を説明しない
   - 失敗を隠蔽する
   - 知識を独占する

### 注意すべきこと

1. **過度な最適化**
   - 今必要な機能以上を作らない
   - パフォーマンス最適化は測定してから
   - YAGNIを常に意識する

2. **複雑性の増大**
   - シンプルな解決策を第一に考える
   - 複雑さは正当化が必要
   - 定期的にリファクタリングする

3. **ドキュメントの陳腐化**
   - ドキュメントはコードと共に更新する
   - 古いドキュメントは削除する
   - 自動生成可能なドキュメントを活用する

## 指針

### 意思決定のフレームワーク

1. **この変更はユーザーに価値を提供するか？**
2. **この設計は将来の変更を容易にするか？**
3. **この実装は他のコンポーネントに影響を与えるか？**
4. **このコードは他の人が理解できるか？**
5. **この決定はドキュメント化されているか？**

### 優先順位の付け方

1. **セキュリティ** > **正確性** > **パフォーマンス** > **機能性**
2. ユーザーの安全とデータの保護が最優先
3. バグのない動作が第二優先
4. 十分なパフォーマンスが第三優先
5. 新機能の追加は上記を満たした上で考慮

## 結び

これらの信念は、プロジェクトの成長とともに進化していきます。
重要なのは、**これらの原則を意識し、意図的な選択をすること**です。

すべてのチームメンバーとエージェントは、これらの信念を共有し、
日々の意思決定に活用してください。
